# Tic Tac Toe Plus — Game Design Document

Статус: рабочий черновик  
Последнее обновление: 3 сентября 2026 года

Это единый файл геймдизайна и планов игры. Новые решения, задачи и статус их выполнения обновлять здесь; отдельные документы могут содержать технические инструкции и измерения, но не самостоятельные конкурирующие планы. Подробности коллекций и UI/UX находятся в разделе 14, общий порядок работ — в разделе 22, аудит графики — в разделе 26.

Этот документ фиксирует текущее направление развития самостоятельной веб-версии Tic Tac Toe Plus. Все числа, награды и сроки предварительные и могут меняться после прототипирования и сбора статистики.

## 1. Цели проекта

- Создать короткую соревновательную карточную игру на основе крестиков-ноликов.
- Поддержать локальную игру, ботов, roguelike и сетевые матчи.
- Построить честный рейтинговый режим с сезонами и историей матчей.
- Добавить долгосрочную прогрессию без преимущества за оплату в ranked.
- Выпускать новые механики через стабильные сезонные наборы правил.
- Разрабатывать игру средствами бесплатных сервисов либо собственного маломощного backend. Обязательные платные сервисы не закладывать; платный тариф или новая аренда допускаются только после отдельного решения владельца.

## 2. Текущее состояние

В игре уже существуют:

- локальный режим;
- обычный бот;
- прототип roguelike;
- онлайн через Photon Realtime;
- колоды и коллекция карт;
- лёд и набор связанных с ним карт;
- локально-первичный кошелёк, коллекция и покупки с отложенной синхронизацией серверного аккаунта;
- Cloudflare Worker и подключаемое хранилище D1.

### 2.1. Статус реализации backend

- D1 выбран и объявлен как постоянное хранилище.
- Создана первая схема аккаунтов, профилей, сессий, кошельков, инвентаря и reward ledger.
- Реализован гостевой аккаунт с серверной сессией.
- Привязка гостевого прогресса к Google реализована в клиенте и backend; для включения требуется OAuth-конфигурация Google Auth Platform.
- Discord остаётся следующим провайдером привязки гостевого аккаунта.
- Добавлены общие ограничения частоты API-запросов с атомарными счётчиками в D1; отдельные лимиты для создания гостей, Google-входа, чтения, записи и админки.
- Основа админки `/admin`: Google-вход в браузере, серверный список разрешённых аккаунтов, точный поиск, профиль, кошелёк, инвентарь, последние операции валюты и аудит просмотров. Баны, компенсации и управление сезонами пока не реализованы.
- Веб-админка использует существующий Google OAuth client; адрес сайта должен быть разрешён в его Authorized JavaScript origins. Разрешённые администраторы задаются только серверной переменной, не кодом клиента.
- Подробности текущих лимитов и проверки: `docs/backend-foundation.md`.

Текущий roguelike состоит из последовательных этапов с ростом поля и счёта, выбором карты и повышением максимальной маны. Текущий бот использует одноходовую оценку атаки, блокирования и центра поля.

## 3. Основные продуктовые решения

- Текущий backend: Cloudflare Workers и D1 через Sites. Для авторитетных матчей рассматриваются бесплатные Durable Objects либо собственный маломощный сервер; выбор зависит от доступности бесплатных квот и фактической нагрузки.
- Photon используется только на переходном этапе разработки и для временного casual-режима.
- Ranked работает только через авторитетный игровой сервер.
- Сезон длится 8 недель.
- У каждой коллекции собственный пропуск на 100 уровней; сейчас основная коллекция и лёд.
- Ranked ruleset не меняется в течение сезона.
- Premium-награды не дают карты, силу или иное преимущество в ranked.
- Друзья реализуются без чата.
- Собственный маломощный backend допустим с раннего этапа. Новую платную аренду, Redis, платную аналитику и другие обязательные подписки не подключаем автоматически.
- Адрес Sites используется владельцем для проверки; публикацией клиентской версии на itch.io владелец управляет отдельно.

## 4. Сетевая архитектура

```text
Клиент
├── статические файлы → Cloudflare Assets
├── профиль, друзья, сезоны → Worker API → D1
└── рейтинговый матч → WebSocket → Durable Object матча
                                      └── результат → D1
```

### 4.1. Ответственность компонентов

Cloudflare Worker:

- авторизация и сессии;
- профиль и облачный прогресс;
- инвентарь и валюты;
- друзья и блокировки;
- сезоны и боевой пропуск;
- таблицы лидеров и история;
- промокоды;
- административные операции.

D1:

- постоянные данные аккаунта;
- завершённые матчи;
- рейтинги и сезонный прогресс;
- награды и история операций;
- санкции и аудит.

Durable Objects:

- matchmaking;
- один авторитетный объект на матч;
- WebSocket-соединения игроков;
- состояние матча, таймеры и переподключение;
- проверка каждого игрового действия;
- единственная доверенная фиксация результата.

### 4.2. Авторитетный матч

Матчевый сервер:

- назначает стороны;
- фиксирует колоды, версию правил и RNG seed;
- принимает действия, а не готовое состояние;
- проверяет очередь хода, стоимость и допустимость цели;
- применяет действие через общий игровой движок;
- рассылает подтверждённое состояние;
- обрабатывает сдачу, таймаут и потерю соединения;
- один раз записывает итог матча и изменение рейтинга.

Клиент не может самостоятельно назначить себе победу, валюту, опыт или рейтинг.

### 4.3. Переход с Photon

1. Локальный режим и бот остаются без изменений.
2. Текущий Photon остаётся временным casual-режимом.
3. Новый ranked создаётся на авторитетном сервере: бесплатные Durable Objects при доступности либо свой маломощный backend.
4. После стабилизации casual также переносится на выбранный авторитетный сервер.
5. Photon удаляется перед коммерческим запуском либо сохраняется, только если его условия и бесплатные ограничения подходят проекту. Платный тариф не является запланированной обязательной зависимостью.

### 4.4. Офлайн-прогресс и переносимость backend

Android-клиент запускает одиночную игру из полного локального снимка и не ждёт Cloudflare. Без доступа к API работают бот, локальная игра, roguelike, колоды, магазин за игровую валюту, коллекция, опыт и получение уже доступных наград. Google-привязка, удалённое удаление аккаунта, административные функции, реклама без связи с рекламной сетью и любые сетевые матчи требуют подключения.

Каждое локальное изменение сначала атомарно отражается в снимке устройства и добавляется в упорядоченную очередь с постоянным `operation_id`. При восстановлении связи клиент отправляет операции по порядку и удаляет каждую только после ответа сервера. Покупка использует один детерминированный seed из `operation_id`, поэтому локальный и серверный результат пачки совпадают. Повторная доставка безопасна благодаря серверным квитанциям. Если один аккаунт менялся на нескольких устройствах, после обработки очереди итоговый серверный снимок разрешает конфликт; несинхронизированные данные другого устройства нельзя считать резервной копией.

Граница переноса не зависит от Cloudflare: чистые локальные редьюсеры находятся в `app/game/local-player-progress.ts`, формат очереди — в `app/game/progress-operation-queue.ts`, общий цикл подтверждений — в `app/game/progress-sync.ts`, текущий HTTP-адаптер — в `app/game/player-progress-client.ts`. Адрес Android API задаётся конфигурацией. Собственный слабый сервер может сохранить контракты HTTP и `operation_id` либо заменить только транспортный адаптер; игровому UI и локальному хранилищу миграция поставщика не нужна.

Этот режим предназначен для текущей неавторитетной одиночной прогрессии. Клиентский локальный баланс нельзя использовать как доказательство платёжной покупки, результата ranked, места в ладдере или ценной общей экономики. Такие операции должны оставаться авторитетными на выбранном сервере и не выполняться офлайн.

## 5. Оценка инфраструктуры

Бюджетное ограничение: бесплатные сервисы либо уже доступный собственный маломощный backend. Не обещаем число игроков без нагрузочного теста.

Фактическое размещение — управляемый Cloudflare D1 через Sites. Личный Cloudflare-аккаунт владельца для создания этой базы не использовался; тариф D1 Free, реальные квоты Sites, регион и сроки резервного хранения не подтверждены. Подробности и незакрытые инфраструктурные задачи: [docs/infrastructure.md](docs/infrastructure.md).

Ниже только справочные квоты обычного Cloudflare Free, а не гарантии текущего Sites-размещения. Перед собственным размещением их нужно перепроверить:

- до 100 000 динамических Worker-запросов в день;
- статические ресурсы не расходуют этот лимит;
- D1 включает 5 миллионов прочитанных и 100 000 записанных строк в день;
- до 500 МБ на одну бесплатную базу и до 5 ГБ на аккаунт;
- Durable Objects доступны на бесплатном тарифе;
- D1 Free позволяет восстановление в пределах 7 дней.

Лимиты считаются по реальной стоимости операций, а не только по количеству HTTP-запросов: сессии, инвентарь, журнал валюты, счётчики и индексы расходуют квоты базы. Текущая защита API делает один запрос счётчика на разрешённое обращение; отклонённые повторы кратко кешируются в ограниченной памяти процесса. Это не защита от распределённой DDoS-атаки и не гарантия работы после исчерпания бесплатной квоты.

При приближении к лимитам сначала уменьшаем частоту обращений, убираем polling, ограничиваем историю и нагрузку, затем рассматриваем перенос на свой backend. Платный тариф — только отдельное согласованное решение, не автоматический следующий этап. Если база недоступна, защищённые API возвращают временную ошибку и не меняют серверные записи; текущая одиночная прогрессия продолжается локально и ставит разрешённые операции в очередь.

Требования к варианту на слабом сервере:

- один backend-процесс и SQLite с WAL на локальном диске, без обязательных Redis, Kubernetes и отдельных микросервисов;
- матч обновляется по действию или таймеру, без постоянной высокочастотной симуляции;
- конечные размеры очередей, комнат, кешей и ответов; ограничение числа одновременных матчей по нагрузочному тесту;
- запросы по индексам, небольшие порции данных, резервное копирование и проверка восстановления;
- общий движок правил и сетевой протокол не зависят от облачного поставщика;
- перенос потребует серверного адаптера HTTP/WebSocket и хранения; готового запуска текущего Worker на VPS пока нет;
- CPU, RAM, диск и канал собственного сервера пока неизвестны: бюджет ресурсов и ёмкость определяются после их уточнения, а не предполагаются.

Альтернативы:

- Firebase подходит технически, но добавляет второго инфраструктурного поставщика и имеет более низкие бесплатные дневные квоты Firestore.
- Supabase подходит как запасной вариант, но потребует переноса backend и базы.
- GitHub Pages не предоставляет базу и безопасный динамический backend.
- Google Apps Script и Google Sheets допустимы только для прототипов или внутренних инструментов.
- Уже имеющийся маломощный сервер — равноправный бюджетный вариант, если хватает ресурсов и обеспечены обновления безопасности и резервные копии.

## 6. Аккаунт и профиль

### 6.1. Вход

- При первом запуске создаётся гостевой аккаунт.
- Гостевой прогресс можно привязать к Google или Discord.
- Пароли и восстановление по email не реализуются на первом этапе.
- Способ хранения сессии выбирается платформенным адаптером и не влияет на игровую логику.
- В браузере сессия хранится в защищённой HttpOnly cookie.
- В Android-сборке сессия хранится через нативный защищённый storage, связанный с Android Keystore.
- Сервер поддерживает cookie для браузера и bearer token для доверенного нативного клиента.
- Выбор адаптера выполняется автоматически по доступности нативного bridge, а не по user agent.
- При недоступности нативного bridge используется браузерная cookie-стратегия.
- При привязке гостевой прогресс переносится без дублирования наград.

### 6.2. Платформенная сессия

Клиент работает только с единым интерфейсом сессии: получить текущий аккаунт, создать гостя, завершить сессию и обработать истечение авторизации. Реализации хранения изолированы в платформенных модулях.

- Web: токен не доступен JavaScript и передаётся браузером через HttpOnly cookie.
- Android: токен возвращается только нативному клиенту и сохраняется в зашифрованном хранилище.
- Сервер хранит только хеш токена и умеет отзывать отдельную сессию устройства.
- У каждого устройства отдельная сессия; выход на одном устройстве не завершает остальные.
- Удаление приложения может удалить гостевую сессию, поэтому восстановление прогресса гарантируется только после привязки Google-аккаунта.
- Переход Web → Android и Android → Web не создаёт новый прогресс после входа в привязанный аккаунт.

### 6.3. Профиль

- внутренний неизменяемый user ID;
- уникальный публичный код;
- ник с правилами допустимых символов;
- аватар;
- рамка;
- титул;
- выбранные косметические предметы;
- дата создания и последний вход;
- настройка приватности приглашений.

## 7. Сетевые режимы

### 7.1. Casual

- не изменяет рейтинг;
- допускает игру с другом;
- может использовать экспериментальные правила;
- используется для тестирования будущих механик;
- выход учитывается в статистике, но не приводит к строгим сезонным санкциям.

### 7.2. Ranked

- только авторитетные матчи;
- стабильный ruleset на весь сезон;
- серверная проверка колод;
- рейтинговый matchmaking;
- переподключение в течение 60 секунд;
- добровольная сдача;
- возрастающее наказание за систематические выходы.

### 7.3. Экран мультиплеера

Кнопка «Мультиплеер» в главном меню в будущем открывает отдельный внутриигровой экран, а не сразу запускает поиск матча. Это функциональный центр сетевой игры: по структуре он может напоминать подход Hearthstone, но не копирует его визуальное оформление.

На экране отображаются текущий ранг и сезонный прогресс, выбор сохранённого пресета колоды, проверка совместимости колоды с выбранным режимом, отдельные действия для обычной и рейтинговой игры, приглашение друга и дополнительная сетевая информация. После выбора режима поиск соперника открывается следующим состоянием этого раздела. Экран должен расширяться новыми сетевыми функциями без перегрузки главного меню.

## 8. Рейтинг и matchmaking

### 8.1. Рейтинг

Используется Glicko-2:

- рейтинг;
- неопределённость рейтинга;
- волатильность;
- 10 калибровочных матчей;
- отдельное состояние рейтинга для каждого сезона.

Видимые лиги:

1. Bronze
2. Silver
3. Gold
4. Platinum
5. Diamond
6. Master

Игрок видит лигу, дивизион, числовой рейтинг и изменение после матча.

### 8.2. Подбор соперника

- Начальный диапазон поиска узкий.
- Каждые 10 секунд диапазон расширяется.
- Учитывается регион и задержка.
- По возможности не назначается тот же соперник, что в двух последних матчах.
- Дружеские матчи никогда не меняют рейтинг.

### 8.3. Новый сезон

- рейтинг частично приближается к стартовому;
- неопределённость увеличивается;
- прошлая история сохраняется;
- прошлый результат отображается в профиле;
- для Master может применяться снижение за долгую неактивность.

- недельные задания;
- сезонная casual-ротация;
- награды за максимальную достигнутую лигу;
- отдельные награды за итоговый Top.

Этапы закрытия сезона:

1. Ranked закрывается в указанное время UTC.
2. Фиксируется leaderboard snapshot.
3. Проводится 72-часовая проверка подозрительных результатов.
4. Дисквалифицированные аккаунты исключаются.
5. Награды выдаются идемпотентными операциями.
6. Создаётся новый сезон и выполняется soft reset.

## 14. Коллекции, стихии, колоды и пропуски

Решение от 3 сентября 2026 заменяет прежнее предложение об одном пропуске на 30 уровней. Экономика пока не спроектирована. Здесь собраны требования, реализованный объём и все отложенные изменения этой системы. Тестовое начисление XP пока использует результат клиента и не удовлетворяет требованиям авторитетной экономики из раздела 4.2.

Последнее уточнение владельца: текущий экран пасса — рабочий прототип, его оформление не утверждено как финальное. На присланном скриншоте подписи и элементы съезжают, заголовки «Уровень» и «Бесплатно» сближаются/перекрываются. Владелец отложил исправление до отдельной доработки UI/UX и попросил сохранить весь остаток работ. Задачи ниже не считать выполненными только потому, что основные кнопки и выдача наград уже работают.

### 14.1. Требования к коллекциям и колодам

В магазине должны быть отдельные баннеры основной коллекции, льда, огня и следующих стихий. Сейчас включены только обычные карты и лёд. Карты покупаются из выбранной коллекции; повторки разрешены. Каждая повторка автоматически превращается в 100 опыта своей коллекции. Визуально повторка распыляется и наполняет шкалу, без анимации помещения в колоду. После завершения анимации доступна покупка ещё одной карты.

У каждой коллекции собственный уровень и пропуск на 100 уровней с бесплатной и платной дорожками. Платная дорожка открывается отдельно для каждой стихии. Пока награды — валюта; в дальнейшем будут карты, скины, контент roguelike, валюта и другие виды наград. Приобретение премиума должно открывать возможность получить уже достигнутые платные награды.

Опыт начисляется за игру колодой соответствующего состава: чем больше карт стихии, тем больше её опыт. Обычные карты можно сочетать с любой стихией. В обычном режиме одновременно разрешена одна неосновная стихия. Позже будут разрешённые пары и режимы с конкретными сочетаниями. Игрок должен иметь несколько собственных колод, в том числе разные варианты одной стихии.

Точки отображения: шкалы и сбор наград после игры; интерактивные блоки в главном меню с красным уведомлением о незабранных доступных наградах; маленькая неинтерактивная шкала на каждом баннере. На баннере также показано число ещё не открытых уникальных карт. При нуле — «Коллекция собрана» и анимированное оформление стихии, при этом покупки остаются доступны для получения опыта из повторок.

### 14.2. Что реализовано сейчас

- Реестр двух коллекций и явная принадлежность всех 16 видов карт. В основной коллекции 7 видов, во льду 9. В стартовой коллекции уже открыты 4 обычных вида и 1 ледяной.
- Независимые баннеры, покупка одной или пяти карт с возвращением в пул после каждого выпадения. Любая карта баннера, включая стартовую, может выпасть. При первом получении внутри пачки карта новая; следующие её выпадения в той же пачке — повторки.
- Новая карта сразу попадает в локальный инвентарь и анимацию коллекции. Активная колода больше не меняется из-за покупки. Повторка превращается в опыт той же локальной операции; сервер затем детерминированно повторяет и атомарно фиксирует пачку, списание и опыт.
- У каждой коллекции свои XP, премиум-доступ и полученные награды. Уровень 0 — начальная точка, награда уровня 1 доступна на 1000 XP, уровня 100 — на 100000 XP. Выше 100000 XP прогресс не растёт.
- Экран всех 100 уровней: две дорожки, блокировка будущих/платных наград, однократное получение, доступ к старым наградам после открытия премиума.
- Премиум открывается кнопкой «Открыть премиум · тест» бесплатно и отдельно для каждого пропуска. Это временная тестовая операция, не платёжная интеграция.
- Главное меню показывает компактные кнопки коллекций в один ряд непосредственно над нижней навигацией: рамка, `lvl N` у верхнего края, иконка 32 px, тонкая шкала 3 px без чисел XP. Доступная незабранная награда обозначается красной точкой; числовой счётчик на кнопке больше не показан. Недоступная платная награда сама по себе не создаёт красного уведомления. Разметка рассчитана на шесть коллекций; визуальная проверка на реальных устройствах остаётся отдельной задачей.
- Создание, именование, выбор и удаление колод; текущая колода переносится в первую сохранённую. Новая колода копирует редактируемую. Сохраняются 5–16 уникальных видов, число экземпляров определяется `CARD_COUNTS`. Технический предел библиотеки сейчас 100 колод, он не является продуктовым или платным лимитом.
- После каждого завершённого раунда показано начисление по коллекциям и возможность сразу забрать доступную награду. В локальной игре прогресс получает аккаунт владельца за сторону X. В игре с ботом — сторона игрока. В roguelike учитывается точный список экземпляров текущего этапа, без повторного умножения базовой карты на пять.
- Полный прогресс и неотправленные операции сохраняются на устройстве. Покупки, колоды, профиль, рекламные награды, результаты раундов, XP и получение наград работают сразу; повторная отправка идёт при инициализации аккаунта, восстановлении сети и после каждого нового действия. Смена уже известного аккаунта очищает чужую очередь. Серверный снимок остаётся итоговым при конфликте устройств.
- Серверное хранение в D1, миграция старой колоды без потери карт/валюты; каскадное удаление новых данных при удалении аккаунта. Операции защищены от повторов и гонок, включая две покупки на последний баланс и два получения одной награды.
- Русская/английская локализация, светлая/тёмная темы, отключение движения через `prefers-reduced-motion`.

### 14.3. Числа для прототипа

| Параметр | Значение | Источник решения |
| --- | --- | --- |
| Уровней в каждом пропуске | 100 | Владелец |
| Опыт на уровень | 1000 | Владелец |
| Победа в раунде | 3 XP за экземпляр карты | Владелец |
| Поражение в раунде | 1 XP за экземпляр карты | Владелец |
| Повторка | 100 XP своей коллекции | Владелец |
| Ничья | 0 XP | Временное допущение реализации |
| Выход соперника / техническая победа | Пока без дополнительного начисления | Временное допущение |
| Бесплатная награда каждого уровня | 10 монет | Заглушка для проверки выдачи |
| Платная награда каждого уровня | 25 монет | Заглушка для проверки выдачи |
| Премиум в прототипе | Бесплатное тестовое открытие | Настоящая покупка отложена |
| Цена карты / пяти карт | 50 / 250 монет | Сохранены старые значения, не новый баланс |

Утверждённые ключевые награды платной дорожки каждой коллекции:

| Уровень | Косметическая награда |
| --- | --- |
| 40 | Анимация открытия карт в тематике коллекции |
| 60 | Внешний вид карты в матче |
| 80 | Анимация постановки фигуры |
| 100 | Анимация фигуры на игровом поле |

Эти четыре награды обязательны для каждого пропуска коллекции, достаточно разнесены по второй половине пути и не дают игрового преимущества. Конкретные названия, изображения и эффекты создаются отдельно для каждой стихии. На уровнях 40, 60, 80 и 100 косметическая награда полностью заменяет монеты платной дорожки; двойная награда на этих уровнях не выдаётся.

Опыт считается по составу колоды раунда, а не по числу розыгрышей одной карты. Стартовая колода содержит 8 обычных экземпляров и 1 ледяной: за победу +24 обычного и +3 ледяного XP; за поражение +8 и +1. Дополнительная награда за победу во всём матче пока не начисляется, чтобы не считать заключительный раунд дважды.

| `app/components/game/DuplicateDust.tsx`, `CardPurchaseFlow.tsx` | Анимация повторки и последовательность открытия |

Новые стихии не добавляются через `if (element === ...)` или `switch`. Нужны определение коллекции, принадлежность новых карт, изображения/цвета/переводы. Механики карт остаются отдельной системой: наличие взаимодействия со льдом не должно неявно назначать принадлежность карты коллекции.

У правила колоды есть `maxElements` и `allowedCombinations`. Исключение допускает только элементы из указанной группы. Например, разрешённая пара «лёд + огонь» не разрешает третью стихию. UI и сервер используют общий валидатор. Сейчас активен стандартный режим с одной стихией; переключение конкретных правил по игровому режиму ещё предстоит.

Награды описаны данными и массивом дескрипторов, выдача — реестром обработчиков. Сейчас реализована только `currency/coins`. При введении нового вида нужно расширять дискриминируемый тип, обработчик, серверную транзакцию и компонент награды. Не помещать выдачу предметов в обработчики кнопок. При нескольких денежных дескрипторах в одном уровне сначала агрегировать проводки либо назначить уникальные дочерние ключи: текущий журнал разрешает одну денежную проводку на операцию.

Хранение: `element_progress` содержит JSON состояния и ревизию, `progression_operations` — результат операции с уникальными `(user_id, operation_id)` и `(user_id, revision)`. Одна D1 batch-транзакция фиксирует квитанцию, валюту/инвентарь и следующее состояние. Конкурирующий запрос пересчитывается от новой ревизии. Старый `player_progress.selected_kinds` синхронизируется для игрового движка и совместимости.

### 14.5. Следующие изменения: подробно

#### 14.5.1. Настоящая экономика и покупка премиума

Определить доступные валюты, стоимость карты/пака каждого баннера, стоимость отдельного пропуска, источник оплаты и нужно ли покупать несколько стихий набором. Решить, нужны ли редкости, разные веса выпадения, гарантии новой карты, pity, скидки на пачки и обмен повторок после достижения 100 уровня. Сейчас распределение равномерное, заполненная коллекция не блокирует покупку, XP сверх максимума теряется.

Посчитать скорость прогресса по составу колоды, длительности раунда, win rate и расходам на повторки. Определить ограничения против фарма, отношения обычного/стихийного XP и размер наград. Числа 10/25 монет не считать утверждённым балансом. Рекламную награду и прежние цены тоже пересмотреть вместе с остальной экономикой.

Ввести entitlement на конкретный pass ID/версию и платформенную проверку чека. Обработать повтор webhook, восстановление покупок, отмену, возврат, переключение аккаунта и получение старых наград. Удалить публичную команду `activate-test-premium` до коммерческого запуска. Реальные платежи в этом изменении не подключены.

#### 14.5.2. Доверенная фиксация результатов и сеть

Текущий `/api/progression` принимает тестовые результаты раунда от клиента. Он проверяет режим, состав и допустимые значения, рассчитывает XP сам и защищает повторы, но не доказывает факт победы. При разных идентификаторах клиент способен создать ложные результаты. Это прототип, непригодный для ценной экономики и ranked.

Перед реальной экономикой перенести источник события на авторитетный игровой сервер: серверные match ID и round ID, зафиксированные обе колоды, правила, результат, участники и причина окончания. Повтор доставки одного раунда должен иметь один серверный ключ. Проверить смену аккаунта при незавершённом запросе, переподключение, выход приложения, кратчайшие матчи и защиту от повторного проигрывания старой истории.

В текущем Photon используется общий `game.deckKinds`, полученный от хоста, а не независимые сохранённые колоды двух игроков. Поэтому полную поддержку собственных колод обоих участников и XP гостя в Photon нельзя считать завершённой: сервер отклонит состав с неоткрытыми у гостя картами. Нужны отдельные колоды по игрокам, передача их до старта, проверка по инвентарю и расчёт XP только по собственной стороне. Не разрешать чужие закрытые карты обходом проверки инвентаря.

Для ничьей, сдачи, таймаута, ухода соперника, локальной игры вдвоём и roguelike отдельно утвердить правила XP. Решить, начисляется ли обычный XP за нейтральные карты или вся колода качает выбранный класс. Сейчас обычные карты качают основной путь, ледяные — ледяной; решение зафиксировано как интерпретация запроса.

#### 14.5.3. Контент наград и роль уровней

Добавить типы наград: открытие игровой карты, скин, рубашка, поле, валюта, roguelike-стартовая колода, реликвия, событие, персонаж/класс и произвольный ключ разблокировки. Для каждого: постоянный item ID, количество, перевод, иконка, карточка предпросмотра, обработчик выдачи, поведение при повторном владении, запись истории.

Четыре косметических рубежа платной дорожки уже утверждены в разделе 14.3: уровни 40, 60, 80 и 100. Их не переносить на ранние уровни и не группировать рядом. Реализация должна хранить отдельные постоянные item ID для анимации открытия, внешнего вида карты, анимации постановки и анимации фигуры каждой коллекции, чтобы игрок мог независимо выбирать полученные элементы оформления.

Определить, какие награды допустимы на платной дорожке и в ranked. Последний запрос допускает будущие карты и roguelike-контент, а прежний GDD требовал отсутствие преимущества за оплату в ranked. Распределение таких наград между free/premium пока не решено; не считать все виды контента автоматически разрешёнными для premium ranked.

Решить, влияет ли уровень ещё на что-либо кроме доступа к наградам. Сейчас боевые параметры и контент от уровня автоматически не меняются. В дальнейшем добавлять декларативные требования разблокировок, не проверки числового уровня в разных экранах.

#### 14.5.4. Новые стихии, парные стихии, правила колод

Огонь пока не создавать пустым покупаемым баннером. После появления карт добавить его данные в реестр, магазин, награды и визуальное оформление через общие компоненты. Уточнить, может ли одна карта относиться к двум стихиям и какой путь получает XP за такую карту. Сейчас у карты ровно одна коллекция; парные режимы означают разрешение совместно использовать карты разных коллекций.

Ввести реестр правил режима, передавать выбранный `DeckPolicy` одновременно в редактор, запуск игры и серверную проверку. Добавить сообщение, почему карта несовместима, подсветку допустимых классов, фильтрацию сохранённых колод для режима и тесты запрещённой третьей стихии. Обсудить минимальный/максимальный размер, обязательность базовых карт, лимиты экземпляров и лимит числа сохранённых колод.

#### 14.5.5. Версии и сезоны пропусков

Решить, постоянные ли 100 уровней или они сбрасываются каждый сезон. Сейчас оба пропуска бессрочные, без автоматического сброса. Старые восемь недель относятся к предложению рейтингового сезона; их нельзя автоматически применить к новым путям.

До изменения выданных наград ввести устойчивые `passId`, `rewardId`, версию таблицы наград и правила миграции. Нынешние ключи — `level:track` внутри коллекции. Нельзя менять уже доступную награду под тем же ключом и повторно выдавать её. Решить судьбу незабранных наград, премиума и лишнего опыта при закрытии сезона; автосбор сейчас отсутствует.

#### 14.5.6. UI/UX и визуальная доработка — отдельный незавершённый этап

##### 14.5.6.1. Главное меню: сохранить последние решения владельца

- Не возвращать большие карточки с названием коллекции, «Уровень N / 100» и числовым опытом: владелец отклонил их из-за занимаемого места и появившейся прокрутки меню.
- Сохранить отдельную компактную кликабельную область каждой коллекции с рамкой; сверху `lvl N`, далее иконка, снизу маленький прогресс без текстового значения. Ряд расположен сразу над нижними кнопками «Колода / Магазин / Настройки», свободное место остаётся выше него.
- Сохранить открытие нужного пасса по нажатию и красную точку доступной награды. Для экранного диктора оставить полное название коллекции, уровень и состояние наград; маленькая визуальная подпись не должна делать кнопки неразличимыми.
- Проверить две, пять и шесть коллекций, узкий экран, безопасные области Android, светлую/тёмную тему и английские подписи. Главное меню не должно получать вертикальную прокрутку из-за этого ряда. Дополнительные стихии сейчас не добавлять ради заполнения макета.
- Подготовить узнаваемые иконки коллекций в общей стилистике: сейчас используются изображения из реестра коллекций. Утвердить отдельное поведение при числе коллекций больше шести, сохранив компактность и размер области нажатия.

##### 14.5.6.2. Экран пасса: переделать прототип в законченный экран

- Исправить замеченное на скриншоте смещение текста и элементов. Согласовать ширины колонок заголовка и строк наград: «Уровень», «Бесплатно», «Премиум» не должны пересекаться. Сейчас первая колонка фиксирована на 44 px; её ширина не учитывает длину подписи.
- Выровнять шапку, переключатель коллекций, основную шкалу, карточки наград и интервалы между секциями. Сделать фон под текстом спокойнее, чтобы узор не ухудшал читаемость.
- Добавить явное выделение выбранной коллекции в переключателе. Разделить визуальные варианты общих компонентов для меню и для экрана пасса: правка нижнего ряда меню не должна случайно менять размещение переключателя на другом экране.
- Различать текущий уровень, уже полученную награду, доступную к получению, будущую и закрытую премиумом. Сейчас несколько причин недоступности объединены подписью «Закрыто»; игроку должно быть понятно, чего не хватает.

Список из 100 ступеней сейчас технический; выбрать окончательный способ навигации, быстрый переход к текущему уровню/первой доступной награде и сохранение места просмотра. Длинному экрану пасса прокрутка допустима; запрет лишней прокрутки относится к главному меню.
- Добавить предпросмотр содержимого награды. Текущее представление читает сумму первого денежного дескриптора; оно ещё не готово к карточкам, скинам, контенту roguelike и нескольким предметам на одном уровне. Визуализацию строить по типам наград через общий реестр, не по названиям стихий и не через разрастающийся `switch` в экране.
- [x] Добавить действие «Забрать всё» одной атомарной серверной и локальной операцией с защитой от повторной выдачи.
- [x] Добавить заметное подтверждение получения и состояния загрузки/ошибки/повтора для одиночной и массовой выдачи.
- Убрать из финального интерфейса тестовую кнопку «Открыть премиум · тест», пояснение о бесплатном тестовом доступе и громоздкую техническую строку правил начисления. Правила перенести в уместную справку, а покупку оформить после отдельной разработки экономики и платежей. Прятание кнопки не заменяет удаление публичной тестовой серверной команды.

##### 14.5.6.3. Магазин, повторки, завершённая коллекция

Сейчас завершённый баннер подсвечивается анимированным контуром цвета коллекции, повторка исчезает через размытие/сжатие, шкала заполняется. Финальные художественные эффекты не сделаны.

- Сделать отличимые по стихиям баннеры, сохранив название, число недостающих уникальных карт, состояние «Коллекция собрана» и маленькую неинтерактивную шкалу. Не превращать эту шкалу в ещё одну кнопку пасса.
- Подготовить ледяной/огненный и последующие эффекты контура завершённой коллекции. Выбрать подходящий способ реализации и проверить стоимость эффекта на мобильном устройстве; отдельный шейдер пока не реализован и не является обязательным решением.
- Сделать частицы распыления, которые летят к шкале соответствующей коллекции, звуки распыления, повышения уровня и получения награды. Поведение покупки общее, ресурсы и оформление задаются данными стихии.
- Проверить последовательность «новая карта / повторка» в смешанной пачке, несколько повышений уровня, окончание анимации и появление «Купить ещё одну». Повторка не должна попадать в анимацию помещения карты в коллекцию/колоду; новая карта не должна автоматически менять активную колоду.
- Согласовать отображение опыта у предела 100 уровня. Сейчас фактическое начисление обрезается лимитом; не обещать визуально +100, если сервер добавил меньше или 0. Дальнейшая судьба лишнего опыта — нерешённая часть экономики.
- Сохранить доступность следующего действия при уменьшенном движении, недоступной покупке и ошибке сети; проверить, что анимация не блокирует интерфейс навсегда.

##### 14.5.6.4. Результаты раунда и библиотека колод

- Доработать компактную послематчевую подачу опыта: несколько коллекций, понятный переход между уровнями, доступная награда рядом со шкалой и подтверждение её выдачи. Текущая анимация и кнопка получения работают, но это ещё не финальная композиция экрана.
- Если добавляется сводка полного матча, показывать сумму уже начисленных раундов без повторной выдачи. Отличать начисление от ещё не сохранённого результата и от повторной отправки после восстановления сети.
- Для библиотеки колод доработать выбор активной колоды, заметность её стихии, создание/переименование/удаление, состояние пустой библиотеки и объяснение несовместимости карты с правилами режима. Механические операции уже есть; финальный UX нескольких колод и будущих парных режимов не завершён.

##### 14.5.6.5. Условия готовности UI/UX

Проверить весь путь «главное меню → нужный пасс → получить награду → вернуться», покупку новой карты и повторки, завершённую коллекцию, библиотеку колод и результат раунда. Проверить русский/английский, светлую/тёмную темы, сенсорные области, фокус клавиатуры, читаемые состояния и уменьшенное движение. На узких и невысоких экранах не должно быть наложений подписей, обрезанных кнопок или недоступных действий; отдельно проверить Android safe area. Сохранить результаты ручной проверки. Прошедшие тесты и сборка не подтверждают визуальную готовность, текущий скриншот владельца подтверждает оставшиеся проблемы.

#### 14.5.7. Офлайн, несколько устройств и обслуживание

Полный снимок одиночного прогресса и упорядоченная очередь операций реализованы. Без сети работают покупки за игровую валюту, выдача наград, опыт, профиль и библиотека колод; повтор отправки запускается при старте, восстановлении сети и новом действии. Остаются явное разрешение конфликтов между несколькими устройствами и ограничения доверия к локальным результатам: очередь подтверждает доставку, но не доказывает честность результата матча.

Добавить версию библиотеки в запрос сохранения, чтобы одновременное редактирование на двух устройствах обнаруживалось как конфликт вместо последнего записавшего. Текущая ревизия защищает атомарность выдачи/покупок, но пользовательские изменения всей библиотеки применяются последней записью.

Добавить просмотр пассов и квитанций в админку, контролируемые компенсации, сроки хранения `progression_operations`, индексы/архивацию по реальной нагрузке, метрики покупок/распыления/темпа XP. Не очищать квитанции без решения о максимальном сроке повторной доставки.

- `assets/icon.png` без найденных ссылок и варианты дизайна вне runtime можно архивировать после проверки необходимости исходников. `og.jpg` нужен для предпросмотра ссылки, нативные Android-иконки разных плотностей имеют отдельное назначение; не удалять их как случайные копии.
- Для будущих художественных рамок использовать маленький 9-slice через `border-image`, для заливок — CSS, для повторяемого рисунка — тайл. Атлас и размеры степеней двойки для обычного DOM-интерфейса не вводить автоматически.
- При росте контента предусмотреть проверку состава `public/game`, которую Android-сборка копирует целиком. Большие исходники и варианты дизайна держать отдельно. Нагрузку blur/теней/частиц и фактическую память измерять отдельно от размера файлов.
- Discord уже исправлен: используется светлый SVG, в светлой теме он отображается чёрным, прежний чёрный PNG удалён. Повторная замена или ручная перекраска в Figma сейчас не требуется.

### 14.6. Проверка перед продолжением

Автотесты `tests/element-progression.test.mjs` покрывают принадлежность карт, пары стихий, повторки в пачке, точный расчёт XP, предел уровня, premium, миграцию, библиотеки, повторные и конкурентные операции, откат транзакции, удаление аккаунта. Полный набор тестов, lint и production build обязательны после изменений. Интерфейсные сценарии и Android-сборку проверить отдельно при следующем ручном тестировании; успешные доменные тесты не заменяют проверку анимаций на устройстве.

UI/UX из раздела 14.5.6 можно дорабатывать отдельной задачей уже сейчас, сохранив утверждённый компактный ряд меню. Экономику владелец явно отложил: значения 1000 XP за уровень, 3/1 XP за экземпляр карты и 100 XP за повторку сохранять до отдельного решения; 10/25 монет и тестовый премиум остаются заглушками.

Порядок технических зависимостей: независимые колоды в сети и доверенные результаты → версии наград/entitlements → новые типы контента → парные режимы и дополнительные стихии → отдельная задача на экономику → платёжная интеграция. Финальное оформление экранов, графика и эффекты остаются самостоятельным незавершённым этапом, а не автоматически готовой частью этих механик.

## 17. Roguelike

### 17.1. Цель режима

Roguelike должен давать:

- короткие повторяемые забеги;
- возможность использовать все механики игры;
- интересные сборки колоды;
- знакомство с картами вне ranked;
- мета-прогрессию и косметические цели;
- площадку для необычных правил и боссов.

### 17.2. Структура забега

Три акта. В каждом акте:

- 3 обычных боя;
- 1 событие или магазин;
- 1 элита;
- 1 босс.

Полный забег состоит из 15–18 узлов и должен занимать около 25–35 минут.

Типы узлов:

- обычный бой;
- элита;
- босс;
- магазин;
- событие;
- отдых;
- сокровище.

После боя игрок выбирает одно из предложений:

- новую карту;
- замену карты;
- улучшение карты;
- реликвию;
- лечение или восстановление ресурса;
- валюту магазина.

### 17.3. Боты

Все боты используют одну utility AI-систему с разными профилями весов:

- Новичок делает 30–40% неточных ходов.
- Тактик ставит победу и блок выше комбинаций карт.
- Накопитель сохраняет ману для дорогого действия.
- Рой предпочитает массовую постановку фигур.
- Криомант создаёт и использует лёд.
- Пиромант контролирует ключевые клетки огнём.
- Зеркало подстраивается под последние действия игрока.

Уровни AI:

- Easy: взвешенный случайный выбор.
- Normal: атака, блокирование и оценка позиции на один ход.
- Hard: поиск на два хода с оценкой доступных карт.
- Boss: Hard AI и уникальные правила босса.

### 17.4. Боссы

#### Ледяной Страж

- Каждый третий ход замораживает линию.
- Его лёд существует дольше обычного.
- После потери половины очков начинает разбивать лёд и ставить на его месте фигуры.

#### Король Горна

- Отмечает ключевые клетки огнём.
- Фигура на горящей клетке уничтожается через ход.
- Во второй фазе огонь распространяется на соседнюю клетку.

#### Архитектор

- Создаёт постоянные стены.
- Один раз за раунд отражает или поворачивает поле.
- Во второй фазе перестраивает границы доступной области.

#### Зеркальный Гроссмейстер

- Копирует последнюю сыгранную игроком карту.
- Меняет приоритет между атакой и защитой.
- Во второй фазе получает заранее показываемую усиленную карту каждые три хода.

### 17.5. Мета-прогрессия

- Общий уровень аккаунта даёт косметические награды.
- Roguelike-мастерство открывает стартовые колоды, реликвии и события.
- Первая победа над боссом даёт постоянную косметику.
- Достижения открывают титулы и альтернативные арты.
- Мета-прогрессия расширяет варианты, но не создаёт бесконечный рост характеристик.

Если roguelike-награды влияют на серверный инвентарь, забег должен получать серверный ID, seed и версию правил. Сервер проверяет журнал действий или подтверждает состояние после каждого боя. Клиентский итог забега без проверки не является основанием для ценных наград.

### 17.6. Сложности

- Normal: базовые правила.
- Veteran: более точный AI и менее выгодные бесплатные узлы.
- Nightmare: модификаторы у элит и дополнительные фазы боссов.
- Ascension 1–10: последовательные ограничения после полного прохождения.

Возможные модификаторы Ascension:

- меньше восстановления;
- дороже магазин;
- проклятая карта в стартовой колоде;
- более долгие статусы противника;
- усиленные элиты;
- дополнительная фаза финального босса.

## 18. Механики поля

Каждая новая механика должна содержать три группы карт:

1. Создание эффекта.
2. Использование эффекта в свою пользу.
3. Удаление или обращение эффекта противника.

### 18.1. Лёд

- Замороженная клетка недоступна для обычной постановки.
- Базовый лёд существует два хода.
- Лёд может хранить замороженную фигуру.
- При естественном таянии фигура возвращается.
- Разбивание льда может освободить, уничтожить или заменить фигуру в зависимости от карты.
- Лёд используется как препятствие и как ресурс для комбинаций.

### 18.2. Огонь

- Огонь помечает клетку, но не блокирует её немедленно.
- В конце следующего хода уничтожает фигуру на клетке, если она есть.
- После срабатывания оставляет пепел, блокирующий клетку ещё на один ход.
- Тушение снимает огонь до срабатывания.
- Другие карты получают эффект за число горящих клеток или сработавших очагов.

### 18.3. Будущие механики

Следующий кандидат после проверки огня — электричество:

- заряд на фигурах или клетках;
- цепная реакция по соседям;
- взаимодействие с маной;
- явное предупреждение о будущем срабатывании.

Третья механика не разрабатывается до получения статистики по огню и льду.

## 19. Ротации

- Ranked ruleset стабилен все 8 недель сезона.
- Casual-события могут меняться еженедельно.
- Roguelike использует все доступные механики.
- Карты игрока не исчезают после ротации.
- Новый элемент добавляется не чаще одного раза в два сезона.
- Будущий ranked-набор тестируется в casual не менее двух недель.
- Экспериментальные правила никогда не включаются в активный ranked без смены версии ruleset.

Пример:

- Сезон 1: нейтральные карты и лёд.
- Сезон 2: балансировка льда, casual-прототип огня.
- Сезон 3: нейтральные карты, лёд и утверждённый огонь.
- Сезон 4: балансировка, casual-прототип электричества.

## 20. Баланс и телеметрия

Обязательные метрики:

- win rate первого игрока;
- win rate каждой карты;
- pick rate и play rate карты;
- средняя длина матча;
- среднее число ходов;
- доля сдач и disconnect;
- частота повторных соперников;
- win rate по лигам;
- сила стартовых комбинаций;
- успешность каждого roguelike-узла;
- частота выбора реликвий и наград;
- причины завершения roguelike-забега.

Баланс оценивается отдельно для casual, ranked и roguelike. Нельзя переносить вывод о силе карты из одного режима в другой без проверки.

## 21. Административные инструменты

Пустая конфигурация закрывает доступ всем. Поиск ограничен точным ником, публичным кодом или ID; просмотр аккаунта записывается в `admin_audit_log`. Токены сессий и идентификаторы OAuth-провайдера в ответы админки не передаются.

Остальные административные действия из списка ниже относятся к следующим этапам и ещё не реализованы.

- просмотр профиля, инвентаря и истории;

Администратор не редактирует баланс напрямую. Любое изменение создаёт отдельную аудируемую операцию.

## 24. Критерии готовности сетевого релиза

- Клиент не может самостоятельно изменить баланс, XP или рейтинг.
- Повтор запроса не создаёт повторную награду.
- Результат ranked подтверждается авторитетным сервером.
- Игрок может переподключиться к незавершённому матчу.
- История и рейтинг совпадают у обоих участников.
- Закрытие тестового сезона выдаёт награды один раз.
- Административные действия записываются в аудит.
- Есть резервное восстановление и проверенная процедура отката.
- Для Google Play выполнен раздел 6.4: работает удаление аккаунта и связанных данных, доступна внешняя страница запроса, политика конфиденциальности и декларации соответствуют релизу.
- Пройдены тесты, lint и production build.

## 26. Справочное приложение: аудит изображений

Дата: 3 сентября 2026. Проверена текущая самостоятельная веб-версия проекта и её Android-ресурсы. Это проверка файлов, прозрачности, ссылок в исходниках и способов отображения. Время загрузки, FPS и фактическая GPU-память в браузере не измерялись. Изображения и код игры не изменены.

**Основной результат**

В игровой веб-графике нет огромных одноцветных квадратов, растровых заливок кнопок или больших текстур рамок. Простые поверхности, обводки и скругления уже реализованы средствами CSS.

Для 33 игровых PNG оценка одного полного RGBA-декодирования каждого изображения составляет 2,85 МиБ: сумма ширина × высота × 4. Сжатый размер PNG и память после декодирования — разные величины.

Обрезать прозрачность у карт без изменения способа отображения нельзя: background-size: contain масштабирует весь исходный холст. После обрезки рисунок станет крупнее или сдвинется. Нужны общий логический размер, координаты рисунка и отступы в данных либо сохранённый SVG viewBox. У ice-encirclement-o и place-more-o холсты уже меньше, чем у соответствующих X-вариантов; при переработке надо проверить согласованность масштаба.

**Правила для подготовки графики под веб**

1. Одноцветная заливка — background-color. Отдельный белый PNG не нужен даже размером 1×1. Простая рамка — border, скругление — border-radius, обычный градиент — CSS gradient.
2. Художественная растягиваемая рамка — небольшой 9-slice-скин через border-image. Углы сохраняются, полосы между ними растягиваются или повторяются. Рисунок центральной области можно включить через fill; одноцветную середину удобнее задать фоном. Скругление рамки нужно предусмотреть в самом скине: border-radius не скругляет border-image. [Справка MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/border-image).
3. Простые значки и контурные рисунки — SVG. Для inline SVG можно использовать currentColor, для внешнего одноцветного силуэта — CSS mask с цветным фоном. Обычный внешний SVG в img не наследует currentColor со страницы автоматически. Разные цветовые темы не требуют отдельных растровых экспортов.
4. Для растра ориентироваться на максимальный размер в интерфейсе, включая увеличение, и плотность экрана. Например, рисунок 190 CSS px для DPR 2 требует порядка 380 пикселей по ширине для отображения без увеличения исходника. Не увеличивать существующий PNG искусственно: это не добавляет деталей. [О плотности пикселей — MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio).
5. Формат выбирать по рисунку. Для графики с чёткими краями и прозрачностью сравнивать PNG и lossless WebP; для сложных иллюстраций — WebP/AVIF с подходящим качеством. SVG полезен для геометрии, но не для встроенной внутрь растровой картинки. AVIF не вводить без проверки поддержки или fallback: проект допускает Android WebView от версии 60. [Форматы изображений — MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types).
6. Проверять альфа-канал и пустые поля, сохраняя ожидаемые координаты и размер рисунка. Проверять экспорт на светлом и тёмном фоне: белая кайма вокруг прозрачности может проявиться только на одном из них.
7. Повторяемая фактура — бесшовный маленький тайл и background-repeat. Для растяжения подходит однородная область; узнаваемый повторяющийся орнамент лучше повторять, чтобы не деформировать.
8. Для обычных img, SVG и CSS-background не нужно автоматически округлять размеры до степеней двойки. Атлас также не является обязательной оптимизацией DOM-интерфейса: он связывает загрузку разных картинок, усложняет замену файлов и может заставить декодировать лишнюю большую поверхность. Решение для WebGL требует отдельной оценки.
9. Исходники высокого разрешения и варианты дизайна хранить отдельно от runtime-папки. В public/game оставлять только нужные экспортированные версии. Общие изображения подключать по одному URL.
10. Для будущих больших иллюстраций предусмотреть srcset/sizes или image-set, загрузку внеэкранных изображений по требованию и версионирование ресурсов для кэша. Главную сразу видимую картинку не откладывать lazy-loading. Эти меры стоит выбирать по измерениям загрузки. [Производительность изображений — web.dev](https://web.dev/learn/performance/image-performance).

Пример настройки 9-slice: условная рамка 48×48 с угловыми областями 12×12. Число 12 в slice означает отступ линии разреза в исходном растре; ширина отображаемой рамки задаётся отдельно.

```css
.ornate-panel {
  border: 12px solid transparent;
  border-image-source: url("/game/ui/panel-frame.png");
  border-image-slice: 12;
  border-image-width: 12px;
  border-image-repeat: stretch;
  background: var(--paper);
}
```

panel-frame.png здесь — пример имени будущего скина, такого файла в проекте нет.

**Что учесть в текущей архитектуре**

Компонент app/components/game/Image.tsx — оболочка над обычным img. Он не меняет размеры файлов и не создаёт WebP или srcset автоматически. Рисунки карт часто подключены через CSS background-image. Уменьшение элемента стилями не уменьшает загружаемый файл.

build/android-public-assets-plugin.ts копирует public/game целиком. Любой будущий забытый экспорт в этой папке увеличит Android-пакет, даже если экран на него не ссылается. Текущий набор маленький, но проверка списка копируемых файлов будет полезна при росте коллекций.

При жалобах на плавность отдельно измерить большие blur, backdrop-filter, тени и анимации. Небольшой размер PNG сам по себе не гарантирует дешёвый кадр, а сложные CSS-эффекты не становятся бесплатными от отказа от растров. В рамках этого аудита замеров кадров не было.

Очередь работ по изображениям ведётся в разделе 14.5.8; здесь сохранены результаты аудита и правила подготовки ресурсов. Массовое уменьшение PNG и упаковка всего в атлас по текущим данным не обоснованы.
